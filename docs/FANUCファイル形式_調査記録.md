# FANUCファイル形式の調査記録（実機で読めなかった件）

実機で「プログラムが読み込めない」「パラメータが読み込めない」が続いた。
渡された実物を1バイトずつ突き合わせて原因を特定した記録。
**なぜアプリがいまの実装になっているか**を残すのが目的。

アプリ内の「詳細ヘルプ → 実機で分かったこと（記録）」に、
現場向けの要約版が入っている。この文書はコード側の根拠まで含む。

---

## 0. 調べ方（これが一番大事）

1. **実機が出したファイルを1つ手に入れる。** これが唯一の正解の見本。
   仕様書より優先する。
2. **バイトで比べる。** テキストエディタでは違いが見えない（改行・不可視文字）。
   `od -An -tx1z` や `data.count(b"\n\r\r")` で数える。
3. **区切り → 使えない文字 → 番号の集合** の順に見る。
4. 分かったことは**必ずテストに落とす**。同じ判断を人が繰り返さないため。

この順でやれば、以下はすべて機械的に出てくる。

---

## 1. 測定プログラムが読めなかった

### 症状
アプリで作った `.NC` が読み込めない。実機が出したプログラムは読める。

### 実物のバイト比較

| 項目 | 実機（読める） | アプリ（読めない） |
|---|---|---|
| 行末の `;` | **0個** | **302個** |
| ブロックの区切り | `LF CR CR`（`0a 0d 0d`） | `LF` のみ |
| コメント | 大文字英数字のみ | `(MEASURE ????)` |
| コメントのカッコ | 入れ子なし | `(--- A (B) ---)` 入れ子 |

### 原因

- **`;` は文字ではない。** 画面に見える `;` は「ブロックの終わり(EOB)」の *表示* で、
  ファイルの中では改行そのもの。`;` はFANUCのISOコード表に無い文字なので、
  書き込むと読込エラーになる。
- **`?` もISOコードに無い。** 日本語のモード名を `errors="replace"` でASCII化して
  いたため `????` になっていた。
- **コメントは最初の `)` で終わる。** `(--- RESET (set 0) ---)` と書くと、
  残りの ` ---)` が不正な指令として読まれる。
- **プレビュー欄で CR が落ちていた。** `_format_program` は `\r\n` で組んでいたが、
  `QPlainTextEdit.toPlainText()` が `\n` に正規化していた。

### 対策（`nd287_app/fanuc.py`）

- `_block()` … `;` を書かない。語間の空白を詰める。コメントは `sanitize_comment()` を通す
- `sanitize_comment()` … 大文字化・ISOコード外を空白へ・入れ子カッコを潰す・40字で切る
- `nc_bytes(text, eob)` … 保存/送信の直前に必ず通す。既定EOBは `\n\r\r`
- `validate(text, cfg)` … 読ませる前の自己点検

検証: 読めなかったファイルは6件検出、実機のファイルは指摘なし。

## 2. 割出軸のアドレス

既定が `X` だったが、`X` はドゥエル `G04 X…` と同じ文字。実機の割出軸は `Z`。
機械ごとに違うので選択式にし、既定を `Z` に。`X` を選ぶと `validate` が警告する。

再現サブプロのO番号も `O9001` → `O1000` へ。
**O8000〜O9999 は保護領域**（パラメータ3202 NE8/NE9）で、書込禁止だと
*転送そのものが弾かれる*。

## 3. パラメータファイル（.prm はダメ / .DAT は通る）

### 原因は2つ

1. **区切り**。読める `.DAT` は `LF CR CR`、読めない `.prm` は `LF` のみ。
   `param_build.write_text` が **元にしたBASICの改行をそのまま引き継いで**いたため、
   PC側の改行のBASICから作った製品ファイルは全部この形になっていた。
2. **その制御装置が持っていない番号が181個**（N09802・N09820〜N09999）。

### 誤った仮説とその訂正

最初「9000番台はメーカ用で書込保護だから」と考えたが**誤り**。
この制御装置は **N27603 まで番号があり、9000番台も大半は実在する**。

正しい判定は **実機のバックアップと突き合わせる**こと。
固定のしきい値を置かない。

- 同じ号機の実機ファイルがあれば、それと比べる
- 無ければ、フォルダにある**実機BASIC全部の番号の和集合**と比べる
  （どの実機も持っていない番号だけが引っかかるので誤検出が少ない）

裏づけ: 新書式の実機BASIC 16本の和集合に N09802・N09820〜N09999 は **1つも無く**、
PC製7本には **全部入っていた**（PC側ツールが足したもの）。

### 対策

- `fanuc_param.prm_bytes()` … 行の中身は1バイトも変えず、区切りだけ実機形式に
- `fanuc_param.validate_prm(text, reference)` … 書式＋番号照合
- `fanuc_param.unknown_numbers` / `drop_numbers` … 実機に無い番号を除いて作れる
- 出力の既定拡張子を `.DAT` に（`settings.param_out_ext`）

検証: `F23BASIC.DAT`（実機）を隠し、PC製の `.prm` と残り15本だけで製品ファイルを
作ったところ、**番号の集合が隠した実機バックアップと完全一致**した。
ただし**値は一致しない**（N02000 の6箇所が違った）。実機のバックアップがあるなら
必ずそちらを使う。

## 4. 拡張子では出どころが分からない

実機BASIC 31本を調べた結果。

| ファイル | 出どころ |
|---|---|
| `F82BASIC.PRM` | 実機 |
| `F18〜F21BASIC.DAT` | PC製 |
| `F22BASIC.txt` | 実機 |
| `F35BASIC`（拡張子なし） | 実機 |

**見分けは中身の区切り**（`nd287_app/param_origin.py`）。

| 区切り | 意味 |
|---|---|
| `LF CR CR` | 実機のパンチ形式 |
| `CRLF×3`（`\r\n\r\n\r\n`） | 実機のものをWindowsのテキストモードで写した（LFとCRが各々CRLFに膨らむ） |
| `LF` / `CRLF` | PCのツールが作った |

補助の手がかり: 実機は `;`・小文字・ASCII外を出さない。

**この判定の限界。** アプリ自身も実機と同じ `LF CR CR` で書くので、
**アプリの出力と実機の出力は区別できない**。判定できるのは
「実機と同じ形式か」までで「実機から出てきたか」ではない。
したがって **BASICフォルダにアプリの出力を置いてはいけない**。
置くと `machine_reference`（実機の番号の和集合）と
`master_fix_rows`（PC製は根拠にしない）の前提が崩れる。
`%` の直後の `(CNCID=…)` は制御装置固有のIDで、どの機械から出たかの手がかりになる。

### 見つかったバグ

`controllers.basic_file_for_unit` が**拡張子（.prm 最優先）で選んで**いたため、
F23 のように実機の `.DAT` とPC製の `.prm` が並んでいると
**読めなかった `.prm` を掴んでいた**。中身（出どころ）で選ぶよう修正。

## 5. BASICの書式が2世代ある

```
新（F18以降）: N01825Q1A1P3000A2P3000        Q1あり・空白なし
旧（F10〜F17）: N01825 A1 P 3000 A2 P 3000    Q1なし・空白区切り
```

`_LINE` が `N\d+Q1` を要求していたため、**8台ぶんのBASICをN形式と認識できず**、
`build_text` が headercsv 経路に落ちて **製品値が入らないままマスタとも違う
ファイル**を出していた。

対策: `_LINE` の `Q1` を任意に、`_SEG` が空白も捕まえて書き戻しで復元する。

検証: 実機BASIC 31本すべてで
「N形式と認識できる／同じ値を書けばバイト不変／1点差替えは1行だけ変化／
読み戻すと一致」を確認。

## 6. 中身が同じBASICは「取り違え」ではない

31本のうち6組がバイト完全一致。当初これを取り違えとして警告したが**誤り**。
**BASICは基本パラメータなので、仕様が同じ号機は中身も同じになるのが正常。**

号機マスタの**ハード仕様**（CNCユニット・制御電圧・軸ごとの容量）と突き合わせ、
**仕様が違うのに中身が同じ**組だけを知らせる（`controllers.classify_duplicate_groups`）。
Ver と SERVO の版数はソフトの版なので見ない。

| 組 | 判定 |
|---|---|
| F24=F80、F25=F26、F27=F28 | 仕様も同じ → 正常 |
| F20=F21 | Y/Z容量が入れ替わっている → 要確認 |
| F18=F19、F33=F34 | 号機マスタに無い → 判定できない |

## 7. 号機で違うパラメータはどこにあるか

実機BASIC 10台を総当たり。積算カウンタ（6750〜6754）と原点（1815/1850）は除外。
差は **4762スロット中 281箇所**。

| 区分 | 箇所 | 中身 |
|---|---|---|
| 仕様で説明できる | 204 (73%) | アンプ58／SERVO版数59／容量+アンプ+SERVO 31／CNCユニット16 ほか |
| サーボ調整値 | 36 | 2000番台。仕様では決まらない（実測・調整の結果） |
| オプション | 31 | N14552〜14637。F31とF82だけON。号機マスタに項目が無い |
| その他 | 10 | — |

**仕様が完全一致するペア（F85-F86）でも39箇所違い**、うち36箇所がA2軸の
サーボ調整値。「同じ容量なら差が無い」は成り立たない。

逆に **容量と1対1に対応していたのは `N2165`（アンプ最大電流）**。
`AMR = 容量 + 5`（20A→25／40A→45／80A→85／160A→165）。
既存の `controllers.amr_to_capacity` がこの規則を持っていた。

`N2165` は **モーター形式(2020)からは決まらない**（同じ255で25と45の両方が実在）。
アンプ側の情報。**制御装置が自動で入れ直すかどうかは未確認**（実機で要検証）。

### 注意（自分がやったミス）

最初、軸を `A1=X, A2=Y, A3=Z, A4=A` と**位置で決め打ち**した。
既存の `controller_from_basic_text` は **1020（軸名のASCIIコード）**で判定しており、
そちらが正しい。実データに X-Y-Z-A-B-C の6軸機があり、位置で決めると
**B/C軸をまったく見ていなかった**。既存実装へ委譲した。

## 8. 個体データは持ち込まない

仕様が同じでも**原点は据付けごとに違う**。

| 番号 | 中身 |
|---|---|
| 1850 | グリッドシフト（原点の実測補正） |
| 1851 / 1852 | バックラッシ補正量 / 早送り時 |
| 1815 #5 | APZ（原点確立済み） |

1850/1851/1852 は **作成時に全軸を0にする**（`param_build.zero_individual`）。
作る軸だけだと他の軸に前の機械の値が残る。
0にする箇所は作成前プレビューに旧→新で出す。

**製品値の側からも外す。** 製品データは「別の号機の完成品と BASIC の差分」
なので、その号機の 1850/1851/1852 が必ず混ざってくる。0にした直後に別の機械の
実測値で上書きされ（しかも軸ラベルは落ちるので別の軸へ入る）、0にする意味が
無くなる。`drop_zero_params()` で製品値から先に外してから0にする。

※一度「製品値を優先する（0化を先にする）」実装にしたが、レビューで
上記の経路が指摘されて誤りと分かった。実データ F30BASIC（全軸0）に
F31BASIC の製品データを当てると、F31 のグリッドシフト -94 が
出力の A4 軸に載ることを確認している。

1815 #5 は「原点確立」の選択で別途扱い、0化の対象には入れない。

実データで対象は3本: `F24BASIC.prm` / `F80BASIC.prm`（1850 A1=5420 A2=9400）、
`F31BASIC.PRM`（1850 A1=-94, 1851/1852 A1=4）。

## 9. 同じ番号が2回出るファイル

`F35BASIC` は 2000番台を中心に **3731個の番号が2回**出ている（多系統）。

`get_value` は最初の行、`values_map` は最後の行を返していたため、
**同じファイルの同じ番号で違う値が読めていた**（2165/A1 が 10 と 45）。
`values_map` を先勝ちにして `get_value`/`set_value` と揃えた。

`set_value` も**最初の1つしか書き換えない**ので、
`duplicate_numbers()` で検出して点検で知らせる。
F35 で製品ファイルを作ると2つ目のブロックに製品値が入らない（未解決の課題）。

## 10. F35BASIC が壊れている（途中の % で読取が終わる）

`F35BASIC` の途中（10958行目）に **`%1P00000000`** という行がある。
本来 `N?????Q1P00000000`（N27000 と N27124 の間）で、先頭7文字が `%` に化けている。

**`%` は読取終わりの記号**なので、制御装置はここで読むのをやめる。
その先の **258行（N27124〜N27609）が丸ごと読み込まれない**。

```
N27000Q1P00000000
%1P00000000        ← ここで終わる
N27124Q1P00000000  ← 以下258行が無視される
N27125Q1P0
…
```

`validate_prm` が途中の `%` を検出するようにした。実データ31本のうち
このファイルだけが該当する。**F35 は実機からバックアップを取り直す必要がある。**

なお F35BASIC は**2つのダンプが連結**された形でもある
（N00000〜N13740 のあと N02016 から番号が巻き戻る）。
これが「同じ番号が2回」の正体で、アプリは最初の1つしか読み書きしない。

容量照合で7本に食い違い（F14 F16 F17 F21 F25 F26 F31）。

**根拠にするのは実機が出したBASICだけ。** PC製は使わない

## 12. ソフトリミット（1320 / 1321）は入れるか選べるようにした

客先パラメータには傾斜軸の可動範囲が `1320`（＋側）・`1321`（−側）に入っているが、
**検査では入れたくないことがある**（検査の割出しが範囲外になる）。

### 実データ（BASIC 31本を全部見た）

全31本が `1320 = -1` / `1321 = +1`（使っていない軸は `0.0`）。**他の値は1つも無い**。
つまり BASIC の出荷時状態＝この値。だから「無効化」で書く値はこれで確定できる。

書き方だけ2世代で違う。旧書式8本は `N01320 A1 P-1`、新書式は `N01320Q1A1P-1.0`。

### 実装（`param_build`）

| 選択 | 動作 |
|---|---|
| `apply`（既定） | 客先どおり書く（従来と同じ） |
| `skip` | 製品値から 1320/1321 だけ外す。BASICの値が残る |
| `disable` | **作る軸だけ** ＋側 -1 / −側 +1 を書く |

- `disable` を全軸にしないのは、同じファイルに入っている相手軸（2軸テーブルの回転軸）
  の設定まで消してしまうため。
- 小数点の有無は **書き込む所の今の値では決めない**。そこには客先値（`-100.0`）が
  入っていることがあり、整数書式のファイルに `-1.0` を書いてしまう。
  同じ行の他の軸に合わせ、決まらなければ書式世代で決める（`_decimal_style`）。
  実機BASIC 25本での検査で最初に見つかった不具合がこれ（旧書式8本が全滅していた）。
- 変わる所は作成前プレビューに出す。`skip` のときも「そのまま（入れない）」と出して、
  黙って落とさない。

## 13. 出力ファイル名に型式・軸・種別を入れる

`T50013078.DAT` → `T50013078_RTT-135_Z-TILT.DAT`。
フォルダにまとめて作ったときに開かずに中身が分かる。

- 制御装置で見る名前なので**半角英数字と `-` だけ**。全角入力は NFKC で半角へ直し、
  漢字・カナは落とす（`param_build.name_tag`）。`傾斜=TILT` / `回転=ROT`。
- 画面のプレビューに出す名前と実際に作るファイル名を必ず一致させるため、
  `create_file(..., name=)` で決めた名前をそのまま渡す。
- 完成製品の差分から2軸を作る経路だけは、どちらの軸が傾斜かがファイルに書かれて
  いないので軸名だけ入れる（頭文字 `TR` が傾斜＋回転を表す）。
- 長い名前が制御装置で困る場合に備えて、設定 `param_name_detail=false` で
  従来の `<頭文字><Seiban>` に戻せる。**メモリカード上で長い名前がどう見えるかは
  実機で未確認**。

## 14. 表示用の書き方が実機用ファイルに漏れていた（原因ではなかった）

> **★訂正。** 最初この節を「読めなかった原因が分かった」と書いたが、**間違いだった**。
> `TR50014175.DAT` が見えなかった本当の理由は 15. のカードの中身で、
> このファイルは中身を直さなくても、カードを空けたら制御装置に出てきた。
> ここに書くのは「実機の書き方と違っていたので、そろえた」という話であって、
> 読めなかった理由ではない。**現物で確かめる前に原因だと言い切ってしまった。**

### 実物の比較

`TR50014175.DAT` は、区切り LF CR CR・`%` は先頭と末尾だけ・`;` なし・全部ASCII・
番号は F23BASIC.DAT と 6440個完全一致で、**点検は全部合格**だった。
値の書き方だけが実機と違っていた。

```
N01320Q1A1P+108.000   ← ＋符号つき・小数3桁
N01260Q1A1P360.000    ← 小数3桁
```

| | 読めなかった出力 | 実機BASIC 31本 |
|---|---|---|
| ＋符号つきの値 | 1個 | **0個** |
| 小数2桁以上 | 10個 | **0個**（80,185個すべて1桁） |

製品データ（人が読む用のヘッダ＋CSV形式 .prm）は `'+108.000` のように表示用の書き方を
していて、それが実機ネイティブのファイルへそのまま書かれていた。`;` と同じ
「表示用の形が機械用ファイルに漏れる」パターン。

### 対策（`fanuc_param.normalize_number`）

原因ではなかったが、**実機が一度も書かない形**であることは事実なので、変数を
1つ減らす意味でそろえておく。`resolve_product_values`（製品値を実機用に解決する
唯一の入口）で書き方をそろえる。**値は変えない**。

```
"+108.000" → "108.0"     "-1.000" → "-1.0"     "108.125" → "108.125"（そのまま）
"3000.000" → "3000"      ※書き込む先が整数で書かれている所だけ
```

`validate_prm` にも「＋符号」「小数2桁以上」を追加し、書く前に気づけるようにした。

### 旧書式では値に触らない（1000倍ずれる危険）

書式世代ごとに小数の使い方が完全に分かれていた。

| 世代 | 台数 | 値の総数 | うち小数 |
|---|---|---|---|
| 旧（Q1なし） | 8 | 50,361 | **0** |
| 新（Q1あり） | 23 | 約38万 | すべて1桁 |

旧世代は値が**最小設定単位の整数**。ここで小数を機械的に落とすと 1000倍ずれる。
そこで旧書式では数値に手を触れず、`validate_prm` が
「この世代は小数を使わない。単位が食い違っていないか確認」と指摘する。
（自分で書いた「整数スロットなら小数を落とす」規則を、実機25本の監査で
旧書式8本が全滅して気づき、直した。）

## 15. ★制御装置に「見えない」の本当の原因はカードの中身だった

`TR50014175.DAT` が制御装置の画面に出てこなかった件の**実際の答え**。

> カードに入っていたファイルを**全部消して、そのファイル1本だけ**にしたら、
> そこで初めて制御装置の画面に出てきた。**長い名前でも出た**。（現物で確認）

つまり、

- ファイルの中身は関係なかった（`+` も小数3桁も原因ではない → 14. の訂正）
- **ファイル名の長さも関係なかった**（`TR50014175` の10文字でも出る）
- カードに入っているファイルの量が効く

「書けたか」と「制御装置に見えるか」は**別の話**。PC側では正常に書けているので、
エクスプローラで見えることは何の保証にもならない。

**同じ症状の可能性があるもの**: 前日の「測定プログラムが制御装置に見えない」も、
同じカードの状態だったのなら同じ原因の可能性が高い（未確認）。

### 分かっていないこと

空き容量そのものが効いたのか、**ファイルの数**（FATのディレクトリ枠。長い名前は
1ファイルで複数の枠を使う）が効いたのかは切り分けていない。両方効きうるので、
アプリでは**両方**を作成前に見せる。

### 対策（`param_build.folder_status`）

出力先を調べて、作成前プレビューと保存前に出す。

| 見せるもの | いつ警告するか |
|---|---|
| 空き容量 | 作るファイルより空きが少ない／2MB未満 |
| フォルダ内のファイル数 | 100個以上（設定 `CARD_FILE_WARN`） |

測定プログラムの保存でも同じ確認を出す（同じカードへ書くため）。

**教訓**: 「制御装置が読まない」と聞いたとき、真っ先にファイルの中身を疑ったが、
今回は**置き場所**の問題だった。次に同じ報告を受けたら、中身を調べる前に
**カードの中身を空にして1本だけで試す**（1分で切り分けられる）。

## 16. DNC運転が始まらない（試験装置の操作盤にDNCが無い）

### 現物（写真で確認）

試験装置の**操作モード**スイッチの位置は8つ。**DNC / RMT が無い**。

```
手動早送り ／ 手動送り ／ 原点復帰 ／ MDI ／ ハンドル ／ メモリ運転 ／ 記憶編集 ／ 自動測定
```

FANUCのDNC運転は「MEM（メモリ運転）モード ＋ **DNCI 信号**（PMC `G0043#5`）ON」で
始まる。ふつうは操作盤の「DNC」ボタンがDNCIを入れる。**その位置が無い＝装置の
ラダーがDNCを想定していない**可能性が高い。パラメータでは直らない（配線の話）。

### 切り分け（2分）

PMCの信号状態画面で `G0043` の `#5` を見る。メモリ運転にして押せるものを押しても
**ずっと 0 ならDNC運転はできない**。

- 0i-MD / 31i / 35i … `SYSTEM` →［PMCMNT］→［信号状態］
- 18i-M / 18i-B / 18i-MB … `SYSTEM` →［PMC］→［PMCDGN］→［STATUS］

### 手元のデータで分かっていること

| 番号 | 値 | 意味 |
|---|---|---|
| `N00020` | **全31本で 4** | 入出力チャネル＝メモリカード。読む側の設定は最初からできている |
| `N00138` | 全31本で `00000000` | この番号の `#7` がメモリカードDNCの有効ビット**だと理解している（裏が取れていない）** |

CNC機種の内訳（号機マスタ）: 18i-M 3台 / 18i-B 1台 / 18i-MB 1台 / 31i-MA 4台 /
35i-MB 3台 / 0i-MD 11台。

### この装置での結論

DNCが使えないなら **記憶編集で登録 → メモリ運転で実行**。測定プログラムは5KB程度
なので登録はすぐ終わる。DNCを使いたかった理由（READで読めない）は、区切り・拡張子・
カードの中身の3件で既に解決している。
