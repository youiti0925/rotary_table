## 2. アプリは何か

**ND287 分割測定アプリ**（PySide6製・Windows用）。
HEIDENHAIN ND287 から測定値を読み、回転テーブルの**割出精度・再現性**を
計算・判定・記録する。LabVIEW製の旧アプリのPython移植版。

付随機能として、FANUCの**測定プログラム(Gコード)生成**と
**パラメータファイル生成**を持つ。いま問題になっているのはこちら側。

```bash
# 実機なしで画面確認
python -m nd287_app --dummy        # または ダミーで起動.bat
# 通常起動
python -m nd287_app                # または ND287分割測定.bat
```

### テストの流し方（★注意あり）

```bash
QT_QPA_PLATFORM=offscreen python -m unittest discover -s tests -q
rm -f settings.json settings.json.bak      # ★必ず消す
```

offscreen実行が `settings.json` を作ることがある（gitignore対象）。
消し忘れると本番設定を上書きする事故につながる。

## 3. ★いま詰まっていること（最優先）

### やりたいこと

メモリカードを持ち歩かずに、**制御装置がPCのフォルダからファイルを直接読む**。

```
制御装置 ──(LAN)──→ PCのFTPサーバー ──→ 公開フォルダ
 取りに行く側            待つ側          .NC / .DAT を置く場所
```

FANUCの**組込みイーサネットのFTP転送は、制御装置がPCへ取りに行く作り**。
だからPC側にFTPサーバーが要る。別ソフトを入れずに済むよう
`nd287_app/ftpserver.py` に自前で実装した（標準ライブラリのみ）。

### どこまで進んだか

| 段階 | 状態 |
|---|---|
| PC側のFTPサーバーが動く | ✅ 完了（画面の「つながるか試す」でOK） |
| 機械からPCへ届く | ✅ 完了（ログに `接続 192.168.1.1` が出る） |
| ログイン | ✅ **直した**（下記） |
| 機械が一覧を要求してくる | ❌ **ここで止まっている** |
| 機械の画面にファイルが並ぶ | ❌ 未到達 |

### 直前に直したこと（9bb75b3）

実機ログで判明。機械は届いていたのにログインで弾かれていた。

```
15:45:24 接続 192.168.1.1
15:45:24 ← USER CNC            ← 機械は大文字で送ってくる
15:45:24 → 331 Password required
15:45:24 ← PASS ***
15:45:24 → 530 Login incorrect  ← ここで弾いていた
```

**FANUCのISOコードに小文字が無い**ので、画面で `cnc` と打っても回線には
`CNC` と出る。サーバーが大文字小文字を区別していたのが原因。
`ftpserver._same_text()` で区別しないようにした。

### 次にやること（この順）

1. **制御装置の「読み込み元」がメモリカードのままでないか確認**
   - パラメータ **`No.0020`（入出力チャネル）**
   - 手元のBASIC30台が `4`（＝メモリカード）、F35だけ `17`
   - **FTPを選ぶ番号は機種で違い、確実な値は分かっていない**
   - → プログラム画面／全データ入出力の**「機器選択」で名前から選び**、
     そのあと0020を読み出して控える（機械に教えてもらう）
2. **公開フォルダが空でないか**（`.NC` / `.DAT` を置いたか）
3. 一覧は出るが機械の画面に並ばない場合 → 設定の**「一覧の形」をMS-DOS形式**へ
4. それでも駄目なら、データ接続（PASV/PORT）を疑う。
   ログに `150 Opening data connection` の後 `425` が出ていないか見る

### アプリ側の切り分け道具（作ってある）

FTPサーバー画面（**ツール ▾ →「FTPサーバー…」**）に3つ。

| 道具 | 何が分かるか |
|---|---|
| **つながるか試す** | PCが自分のサーバーにつなぎ、一覧・ファイル読み出しまで試す。**アプリ側が正常か**だけ分かる |
| **いまどこで止まっている？** | やり取りの記録から判定し、**次に見るところ**まで出す |
| 色の帯 | 黄=まだ届いていない／赤=ログイン拒否／緑=ログイン成功 |

ログには `一覧を渡した（12個・unix形式）` と**個数**も出る。
**0個ならフォルダが空**（機械側の問題ではない）。

## 4. 現場の情報（確認済みの事実）

### 制御装置

```
IPアドレス      192.168.1.1
サブネットマスク 255.255.255.0
MACアドレス     00E0E4808CAB          （FANUCのOUI）
FOCAS2 TCP      8193                  （SERVO GUIDE がこれで繋がっている）
有効なデバイス   内蔵ポート
FTP転送 接続先1  （未設定。ホスト名・ユーザー名・パスワードが空、ポート番号 0 だった）
```

- **SERVO GUIDE が繋がっている** = 配線とIPは確認済み。
  ただし向きが逆（SERVO GUIDEはPC→機械、FTPは機械→PC）なので、
  **Windowsファイアウォールの受信許可だけが新しい関門**。
- 設定画面は **[内蔵ポート]** と **[PCMCIA]** があり、効くのは内蔵ポート側。

### 号機とCNC機種（マスタ/制御装置マスタ.csv）

```
18i-M   3台 (10,11,16)      18i-B 1台 (14)     18i-MB 1台 (17)
31i-MA  4台 (20,21,22,23)   35i-MB 3台 (31,82,84)
0i-MD  11台 (24〜29,80,81,83,85,86)
```

### 試験装置の操作盤（写真で確認）

操作モードの位置は8つ。**DNC（RMT／リモート）が無い。**

```
手動早送り ／ 手動送り ／ 原点復帰 ／ MDI ／ ハンドル ／ メモリ運転 ／ 記憶編集 ／ 自動測定
```

FANUCのDNC運転は「MEMモード＋DNCI信号(PMC `G0043#5`)」で始まる。
**この装置ではDNC運転ができない可能性が高い**（配線の話なのでパラメータでは直らない）。
→ 当面は「記憶編集で登録 → メモリ運転」で運用。FTPは**運ぶ手間を省くため**に使う。

### 軸

**X / Y / Z / A / B / C**。制御装置側はパラメータ `1020`（軸名のASCIIコード）で決まる。
現在の割出軸は **Z**。**X も正規の軸名**（詳細は調査記録 §2 の訂正）。

## 5. 今日やったこと（43コミット・なぜそうしたか）

### A. 「実機で読めない」3件を潰した

| # | 症状 | 真因 |
|---|---|---|
| 1 | 測定プログラムが読めない | 行末に `;` を302個書いていた。`;` はEOBの**表示**で、ファイル内では改行そのもの |
| 2 | パラメータ(.prm)が読めない | 区切りが `LF` のみだった。実機は **`LF CR CR`**。+ その制御装置に無い番号が181個 |
| 3 | 制御装置の画面に出てこない | **カードの中身が多すぎた**（全部消して1本だけにしたら出た） |

**3件目で私は大きな間違いをした。** 値の書き方（`+108.000` や小数3桁）が
原因だと断定して報告したが、**実際は置き場所の問題**だった。
→ 教訓: **「読まない」と聞いたら、中身を調べる前にカードを空にして1本だけで試す。**

### B. パラメータ作成の作り直し

- ソフトリミット(1320/1321)を「入れる／入れない／無効化」から選べるように
- 出力名に型式・軸・傾斜/回転（`T50013078_RTT-135_Z-TILT.DAT`）
- **作成5経路の中身を `param_build.prepare()` に集約**（下記）

### C. 全体監査（6観点×反証）で57件修正

いちばん重かったのは**プレビューが嘘をついていた**こと。
作成処理が5画面にコピペされていて、片方だけ直す事故が2回起きていた。

- ソフトリミット「入れない」でも「108.0を書く」と表示 → 実際は書かれない
- 番号欄に `('01800','L1')` とタプルが出て旧値が空欄（実データで38%）
- かんたん作成とDBは**書く前の点検を1度も通っていなかった**

→ `param_build.prepare()` が
**プレビュー・書き込み・件数・必要バイト数・点検を1回で決める**。
**ここを通さずに作成経路を増やさないこと。**

### D. FTPサーバーを自前で実装

**なぜ既製品を使わないか**: 普通のFTPサーバーはASCIIモードで改行を
`LF`→`CRLF` に書き換える。測定プログラムもパラメータも区切りが `LF CR CR` なので、
それをやられると `CR LF CR CR` になって**また読めないファイルになる**。
`ftpserver.py` は **TYPE A でも中身を1バイトも変えない**（試験で固定）。

## 6. 作業の進め方（今日の教訓・守ってほしいこと）

1. **実機が出したファイルが唯一の正解。** 仕様書や推論より優先する。
2. **推測で禁止しない。** 「X軸はG04 X…と同じだから使えない」と推論して
   選択肢から外し、警告を出し、設定まで書き換えたが**全部誤り**だった。
   現場の実物サブプロが割出軸Xと `G04 X…` を同じプログラムで使っていた
   （しかもそれは最初からテストに入っていた）。
3. **事実と推測を必ず分けて書く。** 「〜です」と「〜のはずです（未確認）」を混ぜない。
4. **分かったことは必ずテストに落とす。** 同じ判断を人が繰り返さないため。
5. **黙って直さない。** 利用者が気づけない自動修正は、原因調査を不可能にする。
6. **間違えたら記録に訂正として残す。** 調査記録の §2 §14 がその例。

## 10. 最初の一手（新セッション向け）

そのPCで動いているなら、**実機に触れる**のが最大の武器。

```bash
cd <アプリのフォルダ>
QT_QPA_PLATFORM= python -m nd287_app --dummy     # 画面が出るか
```

1. アプリ → ツール ▾ → **FTPサーバー…**
2. 公開フォルダを選ぶ（**`.NC` / `.DAT` を何本か置いておく**）
3. **開始** → ファイアウォールは**許可**
4. **つながるか試す** → ①〜④が出ればPC側は正常
5. 機械で一覧を出す → アプリの**「いまどこで止まっている？」**を押す
6. 出た文言のとおりに進める

**PCから機械への疎通確認も忘れずに:**

```
ping 192.168.1.1
```

通らなければ、FTP以前の問題（配線・IP）。
