# 現場で速く書く（画面なしの固定の入口）— 設計と作ったもの 2026-11-25

## 起きたこと（事実）
2026-11-25 朝、受注 50014861（RTV-231）の10件を23号機の Z 軸へ書く作業が、許可から25分たっても1件も書けず中止になった。
機械とのやり取り自体は速かった（控え約16秒・型の確認3件約2秒。PC 側の Claude の報告）。時間の大半は、
**画面なしの入口がアプリに無く、PC 側がその場でスクリプトを作って直していた**こと（文字のまちがいで1回止まり約10分）。
さらに、チャット側の Claude 経由の「書いてよい」を PC 側が本人の許可と認めず、本人が直接書くのを待って止まった。

## 作ったもの（`nd287_app/cli_write.py`・`tests/test_cli_write.py`）
`python -m nd287_app --cli-write …`（exe は `nd287_bunkatsu.exe --cli-write …`）
| 命令 | すること | 機械に書くか |
|---|---|---|
| `plan 受注番号 --unit 23 --axis Z --motor temp --motor-id 293` | つなぐ → 控え → かんたん作成と同じ plan_fn → 一覧 → 承認コード | **書かない**（書く命令を呼ぶと例外になる箱で包む） |
| `write 受注番号 --approve コード [--wait-ready 秒]` | 承認コード確認 → 書ける状態を待つ → 型の確認（初めての型だけ・同じ値を1件）→ 1件ずつ書く → 全行照合 | 書く |
| `check` | 電源を入れ直したあと、書いた件を読み戻す | 書かない |
| `status` | 直近の進み具合の最後の行 | 書かない |
- 作る中身の決め方は画面と同じ（`ParamWizardDialog._machine_job` を offscreen で動かして plan_fn を取る）。新しい決め方は作らない。
- 軸は**推測しない**（`--axis` を渡す）。軸の候補（2165）は、plan が控えから出す一覧で人が確かめる。
- 承認コード＝CNC ID・一覧（番号・ラベル・今の値・書く値）・先に確かめる型 から作る8文字。一覧が変われば変わる。コードが合わなければ1件も書かない。
- 進み具合は1行ずつ、標準出力と `アプリのフォルダ\進み具合\cli_*.log` に出す（exe は窓なしなのでファイルが本体）。落ちたときも「止まりました: 理由」を1行残す。
- 最初の版でやらないもの（理由を出して終わる）: 2軸、セミクロ変換、モーター番号が違うときの2段階（DGPR）→ 画面のかんたん作成で。

## 決めたこと（2026-11-25 チャット側）
- 承認は**利用者本人が PC 側のスレッドに直接**1回（`write … --approve コード`）。チャット側 Claude の伝言は承認にならない（PC 側の許可の仕組みの決まり。回避しない）。
- PW0000（電源の入れ直し）が出た所では、続きの確認・書込は止まる。入れ直してから同じ `write` をもう一度（控えは取り直さない）。**PW0000 が出ている間に FOCAS で書けるかは実機未確認。**

## 未確認（実機）
- 23号機で `plan` を動かして、各段の秒数・軸の出し方が画面と同じか。
- 型の確認で N1821 に同じ値を書くと PW0000 が出るか（朝の4種類目で止まった本当の原因かもしれない。PC 側の推測）。
- exe の配置: 入れ直した先が AppData の外か中か（Windows が Claude アプリの中で別の場所に置き換えていた可能性。デスクトップのアイコンから起動するアプリに届いたか未確認）。

## 実機での確かめ方
1. 読むだけ: `plan 50014984 --unit 23 --axis B --motor product` … 書くものが 0 件になるはず。
2. `plan 50014861 --unit 23 --axis Z --motor temp --motor-id 273` … 一覧が10件・朝と同じ番号と値か。
3. 非常停止を押して `write … --approve コード`。1件ごとの行が止まらず出るか。
4. 電源を入れ直して `check`。
