# 設計: 「受注伝票 X を N号機へ書く」を数分で終わらせる（2026-11-25。設計のみ・未実装）

きっかけ: 2026-11-25、23号機に 50014861（RTV-231）を書く作業が 40 分以上かかり、利用者が中止した
（本番の10件は書いていない。同じ値を書く型の確認が3件だけ）。利用者「次やるまでに早くなるための改善を fable で設計させて」。

## 1. まとめ（作業する人向け）

**今日わかったこと**
- 機械とのやり取りは短い。控えは約16秒（09:15:56〜09:16:12）、型の確認3件は約2秒。
- 40分の大半は、画面の中の処理を画面なしで動かす台本をその場で書いて直した時間。
- 本番の10件は書いていない（書込の記録なし）。型の確認は ビット・実数・2ワード が通った。ワードは実行されていない。

**次回の流れ（案）**
1. **下見**（機械の前にいなくてよい・書かない）: 受注番号と号機 → 前の控えから「どの軸に・何を何件」。軸が思っていたものと違えばここで止まる。
2. **承認**: 下見の一覧（今回なら Z軸・10件）を人が見て「よし」。
3. **本番**（非常停止を押した機械の前で1回）: つなぐ → 控えを取り直す → 下見と同じ中身か比べる → 未確認の型をまとめて確かめる → 1件ずつ書く → 全部読み直して比べる。1行ずつ今どこかを出す。

**安全の決まりは緩めない**: 控えを取ってから書く・非常停止中だけ・許したアラームだけ・同じ機械か・確認済みの型だけ・読み戻し・PW0000 の検出・元に戻す記録。

**利用者に決めてもらうこと**
- **D1 PW0000**: 型の確認で電源入れ直しが要る番号（例 N1821）に同じ値を書いて PW0000 が出ると、今の決まりではその先の確認も本番も断られる。「この作業の中で自分が出した PW0000 だけは続行可」にしてよいか。
- **D2 承認のやり方**: 下見の合言葉（一覧の指紋）を本番の命令に付ける方式か、機械の前の人が PC でキーを押す方式か。
- **D3 入れる場所**: 7章のとおり、Claude から入れたものとデスクトップのアイコンが指すものが別の場所の可能性が高い。AppData の外へ移すか。

## 4. 段と、止まる所と、進み具合

進み具合は1行1件の JSONL:
```
{"t":"2026-11-25T09:16:22","seq":41,"job":"...","phase":"write","step":"N01821 A3","state":"ok","done":4,"total":10,"ja":"N01821 A3 を 2000→45000 に書いて、読み戻しも合いました","data":{...}}
```
- `state`: start / ok / wait / need_decision / stop / fail。最後は必ず `{"phase":"end","exit":番号}`。
- 5秒以上黙る処理は「まだ動いています（控え 3/7）」を出す。
- 出す先はファイルが主（`ジョブ記録/<日時>_<受注>_<号機>.jsonl`、`--progress-file`）。窓なし exe の stdout は未確認。作業者向けの小窓は後の段階（`--show`）。

| 段 | すること | 止まる所（終了番号） |
|---|---|---|
| 0 場所 | アプリの場所・設定・32bit Python・DLL | 無い (2) |
| 1 受注 | 製品データを探す | 0件/複数 (10) |
| 2 機械の事実 | 下見は最新の控え、本番は機械から 2020・2165 | |
| 3 モーターと軸 | 2165 → 2020 → 値の一致 → 人 | 候補が複数 (20、`--axis` で1回選ぶ)。`--expect-axis` と違う (21) |
| 4 号機 | 台帳の CNC ID と号機 | 食い違い (22) |
| 5 BASIC | 点検 | 指摘あり (23。続けるなら `--accept-basic`) |
| 6 計画 | `prepare` → `plan_writes` | blockers (30)。未確認の型は「本番で確かめる型」として出すだけ |
| ―下見はここまで | 計画ファイルと合言葉を出す | |
| 7 つなぐ | 同じ CNC ID か・状態 | 非常停止でない等は `--wait-estop` 秒待つ。過ぎたら (40) |
| 8 控え | フルで取り直す（約16秒） | 不完全 (41) |
| 9 見比べ | 新しい控えで計画を作り直し、承認した一覧と同じか | 違う (42、承認し直し) |
| 10 型の確認 | 5章 | 通らない (50)。値が変わった疑い (51) |
| 11 書く | `focas_ops.run_write` そのまま | 1件でも止まれば残りは書かない (60) |
| 12 全部比べる | `verify_all` | 不一致 (61) |
| 13 記録 | 書込ジョブ.json・書込ログ・規則の結果記録・台帳 | PW0000 なら「電源を入れ直してください」で終わる (0) |

**軸の食い違いを先に出す**: 下見の最初の行に決めた軸と理由（例「製品は 400V の 20A → この機械は 200V なので 40A → 2165 が 40A の軸は Z だけ → Z軸（今のモーター 273）」）と、外した軸の理由（「B軸は 80A なので候補に入りません」）を出す。`--expect-axis B` なら 21 で止まる。

**控えの使い回し**: 本番では使い回さず取り直す（約16秒）。使い回すのは下見だけ。電源の入れ直しは、今ヘルパーが呼べる関数では確実には分からない。使い回すなら「同じ CNC ID・N分以内・param_dump が全行同じ」が条件（節約は約10秒なので最初の版では作らない）。

## 5. 型の確認

- **無言で戻らない**: `verify_needed_kinds` は実行できなかったら必ず理由を返す（例「許していないアラーム PW0000」）。GUI の `verify_kind` も理由を結果欄に出す。
- **1回でまとめて**: 計画の `unverified` を順に回す。型ごとに問題の無い最初の1件に `focas_ops.verify_kind` → 確認済みに足して保存 → 計画を作り直す → その型が未確認の一覧から消えたか確かめる。1つでも通らなければ本番へ進まない。
- **未確認の型は書かない決まりは変えない**（`run_write` の事前点検・ヘルパーの `verified`）。
- **見本の選び方**: 同じ型の中では 0x40 の印が無い行を先に（PW0000 を避けられる可能性）。今回の 2ワード・ワードは全部 0x40 付き → D1 が要る。
- **D1 が「可」のとき**: 作業開始時に無く、自分の確認の書込のあとに増えた PW0000 だけを、残りの確認と本番開始の `_gate` で許す。前から出ていた PW0000 は断る。
- **確認済みの保存**: 「読み直す → その型だけ足す → 保存」の小さな関数に（GUI と上書きし合わない）。
